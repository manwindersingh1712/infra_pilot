## 2026-10-07 Plan 1 Task 1: gosec exclusions, per-site #nosec and symlinks in cloned repos (SEC-1)
Context: CI runs `gosec -quiet -exclude=G204,G304,G306 ./...`. The G304/G306 reason ("paths come from our own config and IDs") is false: Task 21 reads `package.json` and `vite.config.*` and Task 22 writes `Dockerfile` inside an attacker-controlled clone. Worse than a read leak: Task 22's `BuildAndPush` does `os.Stat(repo/Dockerfile)` and, on ErrNotExist, `os.WriteFile`. A repo that commits a dangling symlink `Dockerfile -> /some/host/path` makes Stat return ErrNotExist (it follows the link) and WriteFile then follows the link and writes outside the clone on the worker host. Module-wide exclusions also bypass the Security brief's rule that `#nosec` needs a written reason.
Options considered: keep global exclusions; drop all three; drop G304/G306 and keep G204 excluded with a CI guard against shell invocation; make symlink handling a spec rule vs. a one-off fix in the build code.
Decision: fix now — change plan (Task 1 fix round, Engineer brief, Tasks 21 and 22) and change spec (§5 and §8 text below).
Why: The symlink write is a host-escape from user-controlled input, which is a security hole by our rules; fixing it in the plan text now costs nothing, fixing it after code exists costs a fix round per task. G204 cannot be per-site annotated usefully (the runtime package runs git/docker everywhere by design, always as argument lists), so a global exclusion plus a mechanical guard is the simpler equivalent. G304/G306 have few sites and each deserves its own reason.
Follow-ups:
- Task 1 fix round (Engineer), in `.github/workflows/ci.yml` go job: change the gosec step to `gosec -quiet -exclude=G204 ./...` with the comment `# G204 excluded: the runtime runs git/docker with argument lists by design. The next step forbids shell invocation. Every other finding is fixed or annotated "// #nosec Gxxx -- <reason>" at the site.` Add, before gosec, this step:
  ```yaml
      - name: Forbid shell invocation (G204 is excluded)
        run: |
          if grep -rnE --include='*.go' --exclude='*_test.go' \
            '(exec\.Command(Context)?\(([A-Za-z_][A-Za-z0-9_.]*, *)?|\.Run\([^,]+, *[^,]+, *)"(ba)?sh"' .; then
            echo "::error::Run programs directly with an argument list, never through sh/bash."; exit 1
          fi
  ```
  (Checked against the plan's code: it matches `Run(ctx, dir, "sh", ...)`, `exec.Command("sh", ...)` and `exec.CommandContext(ctx, "bash", ...)`; it does not match `docker run ... alpine sh -c <fixed literal>` in Task 16 `CopyIntoVolume`, container `Cmd` slices, or `_test.go` files, which are legitimate.)
- Engineer brief (`agents/engineer.md`), add rule 9: "Run `gosec -quiet -exclude=G204 ./...` before committing. Fix every finding, or put `// #nosec Gxxx -- <reason>` on that line. A bare `#nosec` or a new module-wide exclusion is not allowed; adding an exclusion is a CTO decision." Add rule 10: "Files inside a cloned repo are attacker-controlled. Open them only through `os.OpenRoot(<repo dir>)` (`root.ReadFile`, `root.Stat`, `root.Lstat`, `root.OpenFile`), never with `os.ReadFile`/`os.Stat`/`os.WriteFile` on a joined path."

## 2026-10-09: Task 14 flush durability (CTO)
- **Context:** the Task 12 reviews found four gaps in the planned `Aggregator.Flush`:
  - the cursor can expire during a ClickHouse outage of more than 15 min, and a crash between insert and cursor write re-inserts one batch (duplicates);
  - one batch of 10000 per run equals `streamMaxLen`, so lines can be trimmed before they are flushed (loss);
  - an empty timestamp is re-stamped on every read;
  - nothing coordinates concurrent flushers.

  Spec §6.7 promises no duplicate rows. During the rollback window (§9), Node must still be able to use the same ClickHouse table.
- **Decision:**
  1. **Fix now: refresh the cursor TTL on every flush pass while the stream exists.** Spec §6.7 is reworded to "best effort". The duplicate from a crash (at most one batch) is accepted. Idempotent inserts are deferred to Plan 3.
  2. **Fix now: drain each stream in a loop until a short batch** (`BatchSize`, at most 20 batches per stream per run). Loss when a producer writes more than about 33 lines/s is deferred to roadmap Phase 6.
  3. **Fix now:** default an empty timestamp at write time in `Redis.Write`.
  4. **Exactly one flusher, the worker's ticker, with no lock.** A lock is deferred to Phase 6, when there are worker replicas.
- **Why:** each fix is small and adds no schema change, no dependency and no rollback risk. The ClickHouse table stays identical to Node's, so rollback remains a plain worker swap.

## 2026-10-09: Managed volume mount path and the Node-era Mongo migration (CTO)
- **Context:** Task 16 (`67aba8e`) mounts every managed volume at `/data`. Staff review STAFF-1 (T16, high) found the problem. `mongo:7` declares `VOLUME ["/data/db","/data/configdb"]`, which the CTO confirmed with `docker image inspect`. Docker therefore puts anonymous volumes on top of the `/data` mount, and Mongo writes into those. The result: each Go redeploy starts with an empty database, and each `docker rm -f` leaves an anonymous volume behind. Node had the same bug (`docker-runner.ts:104` mounts `${volumePath}:/data`), so:
  - Node-era Mongo data has only ever lived in the anonymous volume of the Mongo container currently running. It never survived a Node redeploy.
  - `/tmp/cp-volumes/<id>` holds only the empty `db/` and `configdb/` mountpoint directories that Docker created.

  Two Task 23 rules rest on a false premise:
  - Copying the legacy directory for Mongo copies nothing.
  - The admin123 rule (`hasExistingData` → `legacyMongoPassword`) would start a brand-new, empty Mongo with the publicly known password `admin123`, because that empty legacy directory exists. That is a security regression.

  Redis is not affected: `redis:7-alpine` declares `/data`, and Task 23 passes `--dir /data`.
- **Options considered:**
  - (a) Automatically migrate Node-era Mongo data from the old container's anonymous volume: stop the old container, copy with `--volumes-from`, start the new one, and restart the old one on failure.
  - (b) Mount at the right path, drop the Mongo legacy copy and the admin123 backfill, and move Node-era Mongo data with a manual `mongodump`/`mongorestore` runbook step at cutover.
  - (c) Leave the plan as written.
- **Decision:**
  - **STAFF-1: fix now, (b).**
    - The mount target becomes a `RunSpec` field in the Task 16 fix round, because `RunSpec` lives in Task 16.
    - The image-specific paths and the Mongo rules change in the Task 23 amendment.
    - Node-era Mongo data moves through a runbook step in Task 27.
    - Container removal stays `docker rm -f` without `-v`. The old Node container's anonymous volume therefore survives a Go redeploy, as a fallback for manual recovery.
    - Mongo's `/data/configdb` gets a tmpfs mount, so no anonymous volume is created there. A standalone mongod never uses configdb.
  - **VER-1 (T16):** fix now.
  - **STAFF-2 (T16):** fix now.
  - **STAFF-3 (T16):** fix now.
  - **STAFF-5 (T16):** fix now.
  - **STAFF-6 (T16):** fix now.
  - **STAFF-4 (T16):** fix now, as an optional real-Docker test that is skipped in `-short` mode and when docker is missing. It is the only test that would have caught STAFF-1.
  - Security's T16 report is still pending. Its items will be triaged into this same fix round when it arrives.
- **Why:**
  - Option (a) means stopping and copying a live database, which needs crash-consistency and rollback logic. That is a lot of complexity for one dev VM, and the data it would save never had durability under Node anyway.
  - Option (b) costs one struct field, one map field and a few deleted lines.
