## 2026-10-07 Plan 1 Task 1: gosec exclusions, per-site #nosec and symlinks in cloned repos (SEC-1)
Context: CI runs `gosec -quiet -exclude=G204,G304,G306 ./...`. The G304/G306 reason ("paths come from our own config and IDs") is false: Task 21 reads `package.json` and `vite.config.*` and Task 22 writes `Dockerfile` inside an attacker-controlled clone. Worse than a read leak: Task 22's `BuildAndPush` does `os.Stat(repo/Dockerfile)` and, on ErrNotExist, `os.WriteFile`. A repo that commits a dangling symlink `Dockerfile -> /some/host/path` makes Stat return ErrNotExist (it follows the link) and WriteFile then follows the link and writes outside the clone on the worker host. Module-wide exclusions also bypass the Security brief's rule that `#nosec` needs a written reason.
Options considered: keep global exclusions; drop all three; drop G304/G306 and keep G204 excluded with a CI guard against shell invocation; make symlink handling a spec rule vs. a one-off fix in the build code.
Decision: fix now — change plan (Task 1 fix round, Engineer brief, Tasks 21 and 22) and change spec (§5 and §8 text below).
Why: The symlink write is a host-escape from user-controlled input, which is a security hole by our rules; fixing it in the plan text now costs nothing, fixing it after code exists costs a fix round per task. G204 cannot be per-site annotated usefully (the runtime package runs git/docker everywhere by design, always as argument lists), so a global exclusion plus a mechanical guard is the simpler equivalent. G304/G306 have few sites and each deserves its own reason.
Follow-ups:
- Task 1 fix round (Engineer), in `.github/workflows/ci.yml` go job: change the gosec step to `gosec -quiet -exclude=G204 ./...` with the comment `# G204 excluded: the runtime runs git/docker with argument lists by design. The next step forbids shell invocation. Every other finding is fixed or annotated "// #nosec Gxxx -- <reason>" at the site.` Add, before gosec, this step:
  ```yaml
      - name: Forbid shell invocation (G204 is excluded)
        run: |
          if grep -rnE --include='*.go' --exclude='*_test.go' \
            '(exec\.Command(Context)?\(([A-Za-z_][A-Za-z0-9_.]*, *)?|\.Run\([^,]+, *[^,]+, *)"(ba)?sh"' .; then
            echo "::error::Run programs directly with an argument list, never through sh/bash."; exit 1
          fi
  ```
  (Checked against the plan's code: it matches `Run(ctx, dir, "sh", ...)`, `exec.Command("sh", ...)` and `exec.CommandContext(ctx, "bash", ...)`; it does not match `docker run ... alpine sh -c <fixed literal>` in Task 16 `CopyIntoVolume`, container `Cmd` slices, or `_test.go` files, which are legitimate.)
- Engineer brief (`agents/engineer.md`), add rule 9: "Run `gosec -quiet -exclude=G204 ./...` before committing. Fix every finding, or put `// #nosec Gxxx -- <reason>` on that line. A bare `#nosec` or a new module-wide exclusion is not allowed; adding an exclusion is a CTO decision." Add rule 10: "Files inside a cloned repo are attacker-controlled. Open them only through `os.OpenRoot(<repo dir>)` (`root.ReadFile`, `root.Stat`, `root.Lstat`, `root.OpenFile`), never with `os.ReadFile`/`os.Stat`/`os.WriteFile` on a joined path."

Context: Task 24 (`5fb7e05`) passed the Verifier but Security and Staff requested changes. The CTO had to check its four failure paths (decision 2026-10-08). Read: `deploy.go`, `Activities.{Claim,RetirePrevious,RunContainer,SwitchRoute,MarkDeployed}`, `store/deployments.go`. Facts: `SwitchRoute` is one `UpsertRoute` call with no heartbeat and the workflow only learns the result after it returns, so an error or cancel does not prove nginx was untouched (SEC-1). `RunContainer` heartbeats, so a cancel reaches it, but the workflow returns at once and cleanup can run before `docker run` ends. `MarkDeployed` uses `shortOptions` (about 5 min of retries) (SEC-2). `ClaimDeployment` is per row; `ContainerID` is written only by `MarkDeployed`, so two deployments of one service cannot see each other (STAFF-2). Node had the same race (AMQP prefetch 10, no per-service guard; it only "worked" because deploys of one service were rarely queued together), so this is a pre-existing defect, but Go with one workflow per deployment makes it easy to hit.
Options considered: SEC-1: (a) only `WaitForCancellation`; (b) a `RevertRoute` activity that decides from the DB (previous live deployment) and repoints or removes the route; (c) a cleanup activity that inspects nginx and docker. SEC-2: retry in a disconnected context; retire in cleanup; reconciler only. STAFF-2: service-scoped claim in the Task 24 deploy claim; a starter-side check in Task 25; a per-service workflow (signal-with-start); `workflow.Mutex`. Health timeout: constant vs workflow input vs setter.
Decision: fix now for SEC-1, SEC-2, STAFF-2 (in Task 24, not Task 25), STAFF-1/SEC-3, SEC-4, STAFF-3 (lint step and rename; replay history to Task 27), STAFF-4/5; defer SEC-5, SEC-6 and STAFF-6. Spec §4 steps 3, 8, 9, 12 edited (below).
Why:
- SEC-1: (b)+(a). The invariant is "never remove a container unless the route is known not to point at it". `WaitForCancellation: true` on `RunContainer` and `SwitchRoute` makes the workflow see the real outcome before cleanup. For SwitchRoute the error still does not prove the file is untouched (file written, reload failed; or timeout after reload), so the workflow sets `routeAttempted` BEFORE the call. If an error follows, cleanup runs `RevertRoute` (idempotent: repoint to the newest other live deployment of the service, else remove the route; both are what the Router already offers). Only if `RevertRoute` succeeds is the new container removed. If it fails, the container is kept (serving is more likely than not) and the row is marked failed; a reconciler (Plan 3, existing backlog line) cleans up. Option (c) needs docker and nginx introspection in one activity: more code for the same guarantee.
- The four failure paths are now: (1) before the route is attempted (anything up to and including RunContainer and WaitHealthy): `MarkFailed` + `RemoveContainer(cp-<id>)`, no route change; `RemoveContainer` is idempotent and also reaps a container left by a cancelled `docker run`. (2) `SwitchRoute` errored or was cancelled (route state unknown): `MarkFailed`, `RevertRoute`, then `RemoveContainer` only if the revert succeeded. (3) `SwitchRoute` succeeded and `MarkDeployed` still fails after its extended retries: `MarkFailed`, container kept (serving), `RetirePrevious` not run; warn; Plan 3 reconcile. (4) after `MarkDeployed` (`RetirePrevious`, `StartLogStream`): no cleanup, the row stays `deployed`, the run fails visibly. Managed services have no route, so path 2 does not exist for them; path 1 covers failures after RunContainer, and path 3 applies from `MarkDeployed` on.
- SEC-2: retry in a disconnected context. `MarkDeployed` is the commit point: once the route switched (or the managed container is healthy), it runs in `NewDisconnectedContext` with `commitOptions` (StartToClose 1 min, retry 5 s initial, x2, 1 min max interval, ScheduleToClose 30 min). A cancel or a Postgres blip of a few minutes no longer orphans anything. Retire-in-cleanup is rejected: with the row not deployed `ListLiveDeployments` and the status story get ambiguous, and a deploy whose record never landed should not retire the last known good container. If 30 min of Postgres outage still fails it, the spec §4 step 12 behaviour holds and the Plan 3 reconciler is the safety net (backlog line exists, STAFF-4 T8).
- STAFF-2 lives in Task 24, because it is the state transition that creates the hazard and the starter cannot know the service's live state at start time (the check would still race with the workflow). The service-scoped claim `ClaimDeploy` replaces `claim(queued, deploying)`. One transaction: `SELECT ... FROM "Service" WHERE id = <the deployment's serviceId> FOR UPDATE` (serialises claims of one service; other services are unaffected), then: if this row is already `deploying` return won (own lost result, crash resume); if it is not `queued` return lost; if another deployment of the service is `deploying` and its `updatedAt` is newer than 1 hour return busy; otherwise set `deploying` and return won. Busy is a retryable `ApplicationError` of type `ServiceBusy` under `claimDeployOptions` (StartToClose 30 s, retry every 5 s with coefficient 1, no attempt cap, ScheduleToClose 30 min; retries add no history events). The waiting deployment stays `queued`, builds (`building`) may overlap, and deploys run one after another, in whatever order the retries win; each replaces the previous one, which is what Node's last-writer behaviour did, minus the destruction. No "latest wins/skip" logic: it needs a new status or a policy decision about user intent, and the user who clicked deploy twice expects two deployments. If the 30 min expire, the run takes failure path 1 (the row becomes `failed`, which is accurate: it never ran). Crash recovery: Temporal replays the run, `ClaimDeploy` sees its own `deploying` row and wins. A run that dies without cleanup (terminated by an operator) blocks its service for at most 1 hour because of the staleness rule, which is longer than a deploy can take (RunContainer 10 min x 3 plus health 10 min). `workflow.Mutex` only serialises inside one workflow; signal-with-start per service is a rewrite; USE_EXISTING per service drops deployments.
- Health timeout: a constant. `healthStartToClose = 11 * time.Minute` with no setter, no global, no read in workflow code (kills SEC-3 non-determinism and drift). The config cap `maxHealthTimeoutSeconds` drops from 3600 to 600 in `internal/config` (one constant plus a test), so the activity timeout always exceeds the probe deadline. Task 26 must not call `SetHealthTimeout` (it is removed). Answer to the Engineer: no, that call is not acceptable.
- SEC-4: `ScheduleToCloseTimeout` 90 min on build (30 min x up to 6 attempts would hold a builder for hours). One line.
- STAFF-3: `TestDeployIsDeterministicAcrossRuns` cannot detect non-determinism, so rename it `TestDeployTraceIsStableAcrossRuns` (it is a trace test) and add the real evidence: `workflowcheck` as a CI step (static) now, a committed real history replayed by `ReplayWorkflowHistoryFromJSONFile` in the Task 27 e2e (needs a real server to record).
- SEC-5 stays in the Plan 3 log redaction pass (T23 decision). SEC-6 (`VolumePath` etc. in history): the volume name is `cp-vol-<serviceId>`, not secret; accepted. STAFF-6 (MarkFailed exhausting retries leaves `deploying`): the 1 h staleness rule bounds the damage; the reconciler is Plan 3.
- Real Temporal server: Task 24 may pass without it, because every behaviour above is unit-testable in the test environment and the module is otherwise proven by 540 runs. It is required at Task 26 (smoke) and Task 27 (e2e), where the Verifier runs it: worker kill and resume, cancel during RunContainer and SwitchRoute, two deployments of one service back to back, history replay. This does not block SAAS_ROADMAP; the per-service claim is the base for Phase 3's deploy queue.
- Authorization: `DeployWorkflow` takes only a deployment id and does no ownership check by design (the API checks ownership when it creates the outbox row). Requirement for Task 25 and Plan 2: the starter starts workflows only from outbox rows written by the ownership-checked API; the Temporal frontend (7233) is never published beyond the compose network/localhost, and in production behind mTLS; tenants never reach it.
